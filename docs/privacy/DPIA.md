## 1. Why this document exists, and its limits

GDPR Art. 35(1) requires a DPIA before processing that is likely to result in a high risk to the rights and freedoms of natural persons; Art. 35(7) lists the minimum content (description, necessity and proportionality, risk assessment, measures); Art. 35(2) requires seeking the DPO's advice where a DPO is designated. (Article text read at EUR-Lex on 2026-10-23, see §10.)

**[OPEN]** Whether Art. 35(1) is actually triggered is a decision for the DPO. The Art. 35(3) examples (systematic and extensive profiling with legal effects; large-scale special categories or criminal data; large-scale monitoring of public areas) do not describe the service as designed, but that reading is not a determination: the supervisory authority's Art. 35(4) list was not consulted. This draft is written as if an assessment were required, so that the DPO has a complete basis to decide and, if not required, a record of why.

Facts in this draft are labelled by evidence status:

| Label | Meaning |
|---|---|
| **built** | exists in the repository today and was read for this draft |
| **recorded** | a test result recorded in Progress.md §7 on 2026-10-23 on a throwaway PostgreSQL 18.6 pair; not re-run for this draft |
| **designed** | specified in Architecture.md / DatabaseInfo.md / Rules.md, no implementation read |
| **not built** | absent from the repository |

No application server is deployed anywhere; no real personal data is processed today. Phase 1 builds foundations (Progress.md §2). This DPIA therefore assesses the **intended** processing and the controls that exist or are specified, so that Phase 2 (first ingestion adapters, real customer data) does not start without it.

## 2. Description of the processing (Art. 35(7)(a))

### 2.1 What the service does

`recon` is a B2B API that compares a company's books with the copy each authority holds and produces findings with cited legal basis plus tamper-evident evidence (CLAUDE.md). It is not a filing tool and does not give legal advice; findings state that sources disagree under a cited rule (R-ENG-3).

### 2.2 Roles — **[OPEN]**

| Data | Likely role of the operator (working assumption, Workflow.md §8) | Needs decision |
|---|---|---|
| Customer (tenant) accounting and tax records uploaded for reconciliation | processor (GDPR Art. 4(8): processes on behalf of the controller = the customer) | DPO/counsel to confirm; a processing agreement under Art. 28(3) between the operator and each customer is required if so — **no template exists in the repository** |
| End-user accounts of the operator's own web UI and API-key holders | controller | DPO to confirm; privacy notice not written |
| Operational and security logs | controller | DPO to confirm |

If the operator decides purposes and means of any processing of tenant data (for example product analytics on customer data), Art. 28(10) treats it as controller for that processing. No such processing is designed.

### 2.3 Data subjects

1. **Natural persons appearing in tenant records.** Tenants are companies, but invoices, ledgers and authority records name counterparties and may identify natural persons: sole traders whose VAT or tax identifier is personal data, individual customers on B2C invoices, employees as contact persons. The service does not choose these records; the tenant uploads them. **built:** only metadata about an uploaded object is accepted by the API today (`POST /v1/batches`: `source_type`, `object_uri`, `sha256`, period) — no ingestion adapter parses content yet (Phase 2). **[OPEN]** which record kinds Phase 2 will ingest and whether personal data of consumers is in scope.
2. **End users of the web UI.** **built:** OIDC code flow in the Next.js server, default scope `openid`, session in a sealed `__Host-` cookie that is HttpOnly, Secure, SameSite=Lax (`frontend/lib/auth/`). Identity provider and the claims it releases are undecided (D-3). **[OPEN]**
3. **API-key holders.** **built:** the ledger records `actor_ref = <api key id>` (a UUID) for API commands; the operator tool `recon-admin` writes `recon-admin` as a system actor.

### 2.4 Categories of personal data (from the L4 classification comments, `migrations/w/0002_classification.sql`)

| Class (L4) | Columns (schema.table.column) | Notes |
|---|---|---|
| `pii_id` | `core.legal_entity.vat_id_ct` (ciphertext), `core.legal_entity.vat_id_hmac` (keyed HMAC for exact lookup) | VAT identifiers; personal data when the legal entity is a sole trader. `encrypted=true` / `encrypted=hmac` |
| `pii` | `ledger.audit_event.actor_ref` | pseudonymous reference (API key id today). `encrypted=pseudonymous`, basis `gdpr_6_1_f`, immutable ledger |
| `secret` | `privacy.subject_key.wrapped_dek`, `api.api_key.secret_hash` | key material and Argon2id hashes; not personal data themselves, but their loss or leak affects confidentiality of personal data |
| `financial` | `ingest.source_batch.source_type`, `object_uri`, `failure_reason`; `ingest.source_record.record_kind`, `canonical`; `recon.run.input_batch_ids`, `min_seq`; `recon.finding.check_code`, `severity`, `subject_ref`, `input_record_ids`, `detail` | `canonical` and `detail` are `jsonb` whose design states "no direct PII; refs to core.*" (DatabaseInfo.md §4) — nothing in the schema enforces that |
| `internal` | all other W columns, incl. `core.tenant.name`, `privacy.legal_hold.reason`, `privacy.legal_hold.placed_by` | see §2.5 |
| `public` | `rules.*` | public legal text and rule data |

Replicated schemas: `core, ingest, recon, rules, ledger, privacy, ops` are published from W to R; `api` is **not** published (idempotency keys, API-key hashes never reach R; recorded 2026-10-23: `api` schema absent on R). R additionally holds derived `proj`, `vec`, `fidelity` schemas (designed; `vec` embeds only public legal text, R-AI-2).

### 2.5 Classification items the DPO should look at — **[OPEN]**

- `privacy.legal_hold.placed_by` and `reason`, `core.tenant.name`, `ingest.source_batch.object_uri` and `failure_reason` are classified `internal` or `financial`, but are free text and can contain names of natural persons or identifiers. If so they are personal data and must be reclassified (`pii`) and given `encrypted`/handling rules; L4 only checks that a class is present, not what the content is.
- `ingest.source_record.canonical` and `recon.finding.detail` are `financial` jsonb with a "no direct PII" design rule. Because tenant invoice data is the input, a canonicalisation step that strips or tokenises personal data must exist before Phase 2 ingestion; it does not yet (**not built**).

### 2.6 Purposes and legal basis — **[OPEN]**

Purposes (as designed): (a) reconcile tenant books against authority copies and produce findings with evidence; (b) provide tamper-evident logs of commands; (c) operate, secure and verify the platform (fidelity verification of the replica, monitoring); (d) honour retention, legal-hold and erasure obligations.

The L4 comments carry labels `gdpr_6_1_b` (contract), `gdpr_6_1_c` (legal obligation) and `gdpr_6_1_f` (legitimate interests) per column; the Art. 6(1) points are those in the article read at EUR-Lex. **Caveat for the DPO:** under the processor assumption the legal basis for tenant data is the controller's (the customer's), not the operator's; the labels record the basis the design assumes for each column, and `gdpr_6_1_c` on tax-record columns presumes the customer's own record-keeping duty. They are inputs for the DPO's decision, not a determination. Where `gdpr_6_1_f` is used (`ledger.audit_event.actor_ref`, `ops.fidelity_check`), a legitimate-interests assessment is required and does not exist. **[OPEN]**

### 2.7 Data flow and location

Customer client → API (EU region, designed) → cluster **W** (PostgreSQL, only authoritative writer; per-tenant RLS) → logical replication to cluster **R** (derived read copy; queried by the API) → API → customer. Uploaded source files live in EU object storage (`object_uri`; designed, Object Lock). No tenant data goes to non-EU processors or to SaaS model APIs (R-PRIV-4, R-AI-2). Hosting provider and regions are undecided (D-2): until then no residency claim can be verified at infrastructure level (gate L10 inspects IaC when it exists).

### 2.8 Recipients — **[OPEN]**

None decided. See [SUBPROCESSORS.md](SUBPROCESSORS.md): no processor exists in the repository; D-2 (hosting), D-3 (IdP), D-4 (embedding hosting), D-7 (qualified timestamp service) are pending. The RFC 3161 timestamp request sends a hash of a chain head, not personal data (designed; the hash covers the ledger, whose payloads carry no PII by design).

### 2.9 Retention

Retention is data (`privacy.retention_policy`: jurisdiction, data class, months, source reference), not a constant (R-PRIV-3). **No retention policy row exists in the repository**; the privacy procedures **refuse** erasure and purge when no policy applies (built, `migrations/w/0007_privacy_procedures.sql`). The one EU-level period found while preparing the rule packs is the 10-year record period for the OSS scheme (`rules/EU/oss.yaml` `OSS-012`); Member State invoice-storage periods are national (`rules/EU/vat-invoice-core.yaml` `INV-042`) and **have not been verified** (rules/UNVERIFIED.md). The retention clock implemented in SQL starts at `created_at` of the record and is documented in the migration as a conservative simplification; jurisdiction-specific start rules are not modelled. **[OPEN]** per-country periods and start-of-clock rules need counsel.

## 3. Necessity and proportionality (Art. 35(7)(b))

| Principle (Art. 5(1)) | How the design addresses it | Status |
|---|---|---|
| Lawfulness, fairness, transparency (a) | Basis per column in L4 comments; no privacy notice, no processing agreement template | partly designed; **[OPEN]** notices and agreements |
| Purpose limitation (b) | Purposes in §2.6; embeddings restricted to public legal text; no secondary use designed | designed |
| Data minimisation (c) | Ledger payloads carry opaque references, no PII; findings use opaque `subject_ref`; identifiers stored as ciphertext + HMAC; `ingest.source_record.canonical` "no direct PII" | designed; **not built** (canonicalisation) |
| Accuracy (d) | Source records are immutable inputs identified by SHA-256; findings are re-computable (deterministic engine, R-ENG-1) | designed |
| Storage limitation (e) | `privacy.retention_policy` + `w_retention` purge procedures; erasure by crypto-shred; legal holds | built (SQL), no policy data |
| Integrity and confidentiality (f) | RLS in both clusters, role separation, append-only ledger, envelope encryption, TLS | see §5 |
| Accountability (Art. 5(2)) | This DPIA, the ROPA (generated from the schema), the ledger of privacy decisions, CI gates L4–L7 | partly built |

Data-subject rights (Arts. 12–22) are mostly exercised against the controller (the customer). **built:** SQL procedures for legal holds, erasure decisions and purge, each appending a ledger event in the same transaction (`privacy.place_legal_hold`, `release_legal_hold`, `process_erasure_request`, `purge_expired_batches`). **not built:** the API endpoints for erasure requests and portability export (`/v1/privacy/*` appear only in Architecture.md §17); a way to forward data-subject requests from the operator to the controller. **[OPEN]**

Art. 17(1) lists grounds for erasure; Art. 17(3)(b) disapplies erasure to the extent processing is necessary for compliance with a legal obligation under Union or Member State law (text read at EUR-Lex). The design refuses or defers erasure where a legal hold, a running retention period, or a missing retention policy applies, and **every such decision is written to the ledger** (outcomes `deferred_legal_hold`, `deferred_retention`, `deferred_no_retention_policy` in `crates/recon-store/src/privacy.rs`). Whether a given retention period actually engages Art. 17(3)(b) is a legal determination for counsel and the controller. **[OPEN]**

## 6. Residual risks and design gaps — **[OPEN]**

1. **Encryption is not implemented (R2).** Until M4 exists the columns that are supposed to hold ciphertext have no code path that fills them, and no real identifier may be stored. Phase 2 ingestion must not start without it.
2. **Restoring a backup can resurrect a shredded key (R4) — drafting agent's analysis, not a tested fact.** `privacy.subject_key.wrapped_dek` is erased by an UPDATE on W; a restore of W from a backup taken before the shred contains the wrapped DEK again. The design's second step — disabling the KMS key version — would keep the data unreadable, but no procedure re-applies erasures after a restore. The ledger records every erasure, so a replay procedure is possible; it has to be designed and drilled (see runbook `RestoreDrill`).
3. **Object Lock versus erasure (K-6).** Locked artefacts cannot be deleted before expiry; the design makes them hold only ciphertext. Counsel should confirm that crypto-shredding is accepted as erasure for the controllers' purposes.
4. **The ledger is permanent.** `actor_ref` must never hold a direct identifier. When user actors appear (OIDC, D-3) the reference must be opaque, with the mapping stored in a shreddable table.
5. **Pseudonymised is still personal data.** HMAC lookups (`vat_id_hmac`) and `subject_ref` allow linkage by anyone who holds the HMAC key or both datasets; key custody must be designed.
6. **R holds a complete replicated copy of tenant data.** Access to R is by the `r_api`-style roles with RLS; operators with superuser access are outside RLS. Administrator access control and its logging are not designed. **[OPEN]**
7. **Retention data is missing**, so erasure and purge currently always refuse (conservative failure mode, but also a rights-handling gap if requests arrive).
8. **Sole traders and consumers.** If any pilot country needs B2C data or sole-trader identifiers, the risk picture changes (R1, R2, R7) and this DPIA must be revised before ingestion (R-PRIV-7).
